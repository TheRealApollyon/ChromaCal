# ChromaCal panel frontend

Source for the sidebar panel ChromaCal's Python integration registers via
`custom_components/chromacal/frontend.py`. Built with
[Lit](https://lit.dev) + TypeScript, bundled with
[esbuild](https://esbuild.github.io/) into a single ES module.

## Why the build output is committed

A HACS install just copies `custom_components/chromacal/` onto the user's
HA host — there's no npm/Node available there, and there shouldn't need to
be. So the built bundle,
`custom_components/chromacal/panel_dist/chromacal-panel.js`, is committed
to the repo as a tracked build artifact, same as any other release asset.
**Never hand-edit that file** — it's generated. Edit `src/` and rebuild.

## Rebuilding

Requires Node.js (any recent LTS). From this directory:

```bash
npm install
npm run build
```

That regenerates `../custom_components/chromacal/panel_dist/chromacal-panel.js`.
Commit the regenerated file alongside your source changes.

If Node isn't installed locally, the same build runs fine in a throwaway
container from the repo root:

```bash
docker run --rm -v "$(pwd)/frontend:/frontend" -w /frontend node:22-slim \
  sh -c "npm install && npm run build"
```

## Type-checking (optional, not required for the build)

`esbuild` transpiles TypeScript without checking types. Run the real
compiler separately if you want that:

```bash
npm run typecheck
```

## House View live-verification test assets

`house-view.ts` needs real files in the verification container's `/config/www/`
to test against -- not synthetic/generated placeholders, since the whole
point is confirming real image decode / real glTF parse behavior. These
are the standing assets, real HTTP downloads with verified licenses (not
generated), reused across phases rather than recreated each time:

- **2D**: [File:Little White House floor plan.svg](https://commons.wikimedia.org/wiki/File:Little_White_House_floor_plan.svg)
  (Wikimedia Commons, public domain) -- a real, labeled multi-room floor
  plan, good for confirming marker placement lines up with something a
  user would actually recognize.
- **3D**: `house.glb` -- a small, hand-authored house (walls, a pyramidal
  roof, a door, three windows, a chimney), generated by
  [`scripts/generate-test-house.mjs`](scripts/generate-test-house.mjs).
  Run `node scripts/generate-test-house.mjs house.glb` (from this
  directory, after `npm install`) and copy the output into the
  container's `/config/www/`. No external license question at all --
  it's this project's own authored geometry, not a downloaded asset.
  Confirmed live: orbits correctly, raycasts correctly across its several
  distinct surfaces (walls, roof, door, windows, chimney all separately
  hit-testable), and is unmistakably house-shaped at a glance -- unlike
  every real external candidate that was actually tried first:

  - Khronos glTF-Sample-Assets' `Box.glb` (CC-BY-4.0) is a fine quick
    smoke test, but its `Models/Sponza` sample is NOT a safe substitute
    for anything more -- its actual model files are licensed under the
    CRYENGINE Limited License Agreement (a EULA, not CC0/permissive),
    confirmed by reading `Models/Sponza/LICENSE.md` directly rather than
    assuming "Khronos sample = same license as Box.glb."
  - Poly Haven is entirely CC0, but its model catalog (searched in full --
    521 models, by category and by keyword) has no standalone house,
    cottage, or cabin -- only architectural fragments (gates, facades,
    fortifications). `modular_fort_01` was tried first and works
    (real multi-surface CC0 architecture) but isn't house-shaped.
  - `floor3d-card`'s own repo ships no example model at all; its wiki
    points to an unlicensed third-party `.sh3d` file -- no license
    stated, a worse trap than Sponza's, not just an unclear one.

  `scripts/generate-test-house.mjs` hand-assembles the glTF 2.0 JSON +
  binary buffer directly rather than using three.js's own `GLTFExporter`
  -- that hangs indefinitely under plain Node (silently depends on
  browser-only `FileReader`/`Canvas` APIs even with zero textures in the
  scene; confirmed via Node's "unsettled top-level await" warning, not a
  thrown error).

Neither asset is committed to this repo (they're test fixtures for a live
container, not shipped product code) -- refetch/regenerate them into a
fresh container's `/config/www/` each time one is needed.
